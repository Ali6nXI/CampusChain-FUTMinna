Motivation

The problem this addresses

Solar capacity on Nigerian university campuses is installed building by building. Each array is sized for its own worst case, so it spends much of the day producing more than its host building consumes.

🔌

Surplus is wasted

A hostel array peaks at midday when residents are in lectures. Without storage or a route to a neighbouring load, that generation is simply curtailed — the energy is produced and then thrown away.

🧱

Islands, not a grid

Installations are electrically and administratively isolated. A building running short has no mechanism to draw from a neighbour that is exporting at that exact moment.

📵

No trusted meter record

Manual readings can be disputed and are hard to audit. Any settlement scheme needs a record that participants can verify without trusting whoever keeps the books.

Working Principle

How a trade happens

Six steps, from a physical meter reading to a settled trade recorded on a public blockchain.

The meter reports

A PZEM-004T energy sensor on each building feeder measures voltage, current, power and accumulated energy. An ESP32 reads the sensor and publishes a JSON reading over MQTT every ten seconds. In the current prototype this hardware is faithfully simulated in software.

The backend validates and caches

A Node.js service subscribes to the MQTT topic, checks every message against a strict schema, and rejects malformed payloads instead of trusting them. Valid readings are cached and served to the dashboard over a read-only REST API.

A surplus is listed

When a building has energy to spare, its operator opens the dashboard, connects MetaMask and submits a listing: building name, quantity in watt-hours, and price per watt-hour. The transaction is signed in the wallet — the server never sees a private key.

The buyer approves spending

Before a purchase the buyer signs an ERC-20 approve() granting the trading contract permission to move exactly the required number of CET tokens. This is the standard two-step ERC-20 pattern, and it keeps the buyer in control of the allowance.

The contract settles atomically

buyEnergy() checks the listing is active, transfers tokens from buyer to seller, marks the listing sold and emits a TradeExecuted event — all inside one transaction. Either every part succeeds or the whole thing reverts. There is no state in which payment leaves the buyer without the trade being recorded.

The record becomes permanent

Once the block is mined the trade is part of the public chain. Both parties, the university, and an external auditor can verify it on Polygonscan without needing access to any private system.

System Design

Four layers

Each layer has one responsibility and communicates through a defined interface, so any layer can be replaced without rewriting the others.

📡

1 · Perception

PZEM-004T sensors and ESP32 microcontrollers on building feeders. Measures the physical electrical quantities that everything else depends on.

🌐

2 · Network

MQTT publish/subscribe over Wi-Fi via a HiveMQ broker. Topic campuschain/futminna/{building}, QoS 1, ten-second interval.

⛓️

3 · Blockchain

Two Solidity contracts on Polygon Amoy. EnergyToken is the ERC-20 unit of account; EnergyTrade holds listings and performs atomic settlement.

🖥️

4 · Application

React and Vite dashboard with MetaMask signing, plus a read-only Node.js and Express API that aggregates meter data and contract state.

Evaluation

What has been demonstrated

The central claim of this project is that a peer-to-peer energy trade can be settled between two independent parties with no trusted intermediary. That claim has been tested end to end on a live public network.

✅ A complete trade, verified

Listing 1 (hostel joe, 100 Wh) was purchased by a second, independent wallet. The token balances reconcile exactly: the seller moved 1,000 CET to the buyer, then received 100 CET on the sale, ending at 999,100 of the 1,000,000 minted. The buyer spent 100 of their 1,000 and holds 900. The listing's isActive flag flipped to false in the same transaction.

✅ Non-custodial signing

Listing 6 (ROOM1) was created entirely from the browser through MetaMask. No private key exists anywhere in the backend, and the server cannot move a user's tokens. This was the single most important defect fixed during development.

✅ Contract test suite

Seven Hardhat tests covering listing creation, purchase, cancellation, access control and balance accounting. All seven pass in roughly 0.76 s on a clean clone with no local configuration.

✅ Input validation at every boundary

MQTT payloads are checked against a schema before use — verified by injecting malformed messages, which were rejected. The REST API returns proper 400 and 404 responses instead of failing silently.

Defects identified and resolved

5No network validationUsers on the wrong network saw confusing failuresChain ID 80002 detected, with one-click switching
6Unvalidated MQTT inputA malformed reading could corrupt displayed stateSchema validation on every incoming message
7No API input validationBad requests produced unclear errorsExplicit 400 / 404 / 410 responses
8Serial RPC callsDashboard load time grew with each listingParallel Promise.all with an 8-second cache
9Debug logging in productionConsole noise leaked internal stateRemoved
10Addresses hardcoded in four filesRedeployment meant editing several files, easy to get wrongCentralised in frontend/src/contracts.js

Stated honestly — the oracle problem. This system settles trades correctly given the meter readings it receives. It cannot by itself prove that a reading corresponds to electricity that physically flowed. Bridging trusted physical measurement to on-chain state is an open research problem across the whole blockchain-energy field, not a gap unique to this work. A production deployment would need signed readings from tamper-evident metering hardware. Naming that boundary precisely is part of the contribution.

Reproducibility

Run it yourself

Three services. Node.js 22 or later and Python 3.10 or later are required.

# 1 — get the code
git clone https://github.com/Ali6nXI/CampusChain-FUTMinna.git
cd CampusChain-FUTMinna

# 2 — IoT meter simulator (terminal 1)
cd iot
pip install -r requirements.txt
python mqtt_publisher.py

# 3 — backend API, read-only (terminal 2)
cd backend
npm install
node server.js                    # http://localhost:3001

# 4 — dashboard (terminal 3)
cd frontend
npm install
npm run dev                       # http://localhost:5173

backend/.env

PORT=3001
AMOY_RPC_URL=https://polygon-amoy-bor-rpc.publicnode.com
ENERGY_TOKEN_ADDRESS=0x7223Fb307bD4C48335329CF68098521a59D579Ac
ENERGY_TRADE_ADDRESS=0xE82A1Daad1c4564A4741502c33b4cE4322Da2dc0

There is no PRIVATE_KEY here, and that is deliberate. The backend only reads from the chain. Every state-changing transaction is signed by the user in MetaMask, which means a compromised server cannot move anyone's tokens.

If the dashboard shows zero listings, the cause is almost always the RPC endpoint. The commonly cited rpc-amoy.polygon.technology host is currently unreachable. Use polygon-amoy-bor-rpc.publicnode.com as shown above.
